# MOTIF-RACK ES の調査メモ

MOTIF-RACK ES を S-MU2000 と同じやり方（本物のプログラムを、写したチップの上で走らせる）で
鳴らせるかの下調べ。2026-10-02 に始め、10-08 にサービスマニュアルと突き合わせた。
**まだ何も動いていない。** 分かったことと、足りないものの記録。

> 取り出したプログラムや ROM は配らないこと（[doc/dump/README.md](dump/README.md) の注意書きと同じ）。

> **2026-10-13: 実機で確かめたもの**（[motif-rack-es-capture.md](motif-rack-es-capture.md) の「基準の録音の結果」）。
> 音量の目盛り（0x10 = 6.02dB、高さのパラメーターは 2 乗で効く）、EG の速さの表（8 目盛りで時間が 2 倍、単位はサンプル数、いちばん遅い値が 19.8 秒）、
> ディケイの時間をそろえる式、波形の名前の表と番号の対応、は実機の録音やバルクダンプと合った。
> 下の本文で「見立て」「未確認」と書いてあっても、この 5 点は確かめ済み。

## 更新データの形

Standard MIDI File で、中身は SysEx だけ。MU2000 の `.ydl`（[dump/updater-protocol.md](dump/updater-protocol.md)）と
ほぼ同じで、モデル ID が `6F`。細かい形は `tools/motif/mrfirm_extract.py` の頭に書いた。

```bash
python tools/motif/mrfirm_extract.py firm103.mid -o roms/motif-rack-es/firm103.bin
```

* イメージは 0x2C2800 バイト。圧縮も暗号化もされていない
* 全体のチェックサムは**バイトの総和**（区画の終わりに下位 28bit、全体の終わりに下位 16bit）。
  取り出したものの和が記録と一致する
* 頭の 0x40 バイトは版の文字列（`1.03`）、プログラムは 0x40 から
* Readme によると更新されるのは Firm だけで、Kernel と Data はそのまま。
  **Kernel（更新を受け付ける側と OS）と Data（音色など）はこのファイルに入っていない**

## プログラムの中身（イメージを読んで分かったこと）

| | |
|---|---|
| CPU | SH-3。リテラルの番地から、**RAM の 0x8C020000 に置かれて動く**（フラッシュから RAM へ写してから走る） |
| OS | µITRON（`TRAPA #31` でシステムコール）。OS の本体は Kernel の側にあり、このイメージには無い |
| 周辺 | 0xA4000xxx（SH7727 の内蔵周辺。0xA4000240 からは内蔵の USB） |
| 音源 | 0xB8000000 と 0xB8080000 に 1 個ずつ。番地 = 土台 + ((レジスタ << 8 \| スロット) << 1)。スロット 0x7E・0x7F が制御レジスタ |
| そのほか | 0xB4000000-28、0xB0000000 付近（未調査。プラグインボードやパネルだろう） |
| デバッグ用の口 | シリアルのコンソール（`CONSOLE FUNCTIONS`。メモリのダンプ、タスクの一覧など）。`Wave Dump` もあるが、製品版では中身が抜かれているらしい |
| 検査モード | `Test Program`。Flash IC-32,33 / Wave IC-36〜41 / Main IC-29,30 / Efct IC-26,31 の検査がある |

### 音源チップ経由の波形メモリの読み方（検査のコードから）

0x8C097A84 の関数。MU2000 の SWP30 の「wave direct access」とよく似ている。

| レジスタ | 中身 |
|---|---|
| 0x227F | 0x30 を書く（種類の選択らしい） |
| 0x247E / 0x247F | 番地の上位 16bit / 下位 16bit（16bit の語単位） |
| 0x207E | 0xC000 で読み出し開始、0x8000 で書き込み開始、0 で終わり |
| 0x287E | 状態。**0xC000 のどちらかのビットが立つまで**読んで待つ |
| 0x2E7E | データ（16bit） |

### 波形 ROM の大きさ

検査は ROM を全部読むのではなく、0x8C1CBFDC の表（72 行）にある番地の語を読んで、決まった値と比べるだけ。
表の番地は 0x00000000-0x02FFFFFF の範囲で、0x01000000 語ごとに 3 区画。偶数番地と奇数番地で
別のチップを見ている。つまり **16bit 語で 0x03000000 個 = 96MB**。
表には 72 か所 × 2 語の本物のデータが入っているので、吸い出したものの照合に使える。

## 製品のプログラムに残っている「読み出しの口」（2026-10-08、静的な読みだけ）

MU2000 では、サンプリング用の非公開 SysEx が SWP30 の波形メモリをそのまま読めたので、
無改造で波形 ROM が取れた（mu-wave-romdumper）。同じ種類の口が RACK ES にあるかを探した。
**実機では何も試していない。**

| 口 | 分かったこと |
|---|---|
| コンソールの `wd` / `wn`（Wave Dump） | 0x8C02D25C。番地を聞いて表を刷るが、**波形を読む部分が無い**（スタックの空のバッファを刷るだけ） |
| コンソールの `db` / `dw` / `dl`、`cb` / `cw` / `cl` | CPU の番地をそのまま読み書きする。生きていればフラッシュ（Kernel・Data）が読める |
| コンソールの線 | 割り込みは 0x880 / 0x8A0 / 0x8E0（SH7727 の SCIF1 = IrDA 側の番号）に登録しているが、ハンドラーが直列のレジスタに触っていない（受信は添字を進めるだけ）。SCI（0xFFFFFE80）も SCIF1（0xA4000140）も番地が出てこない。**製品版では線の先が抜かれている見込み**（Kernel の側が面倒を見ている可能性は残る） |
| 検査の波形読み（0x8C097A84） | 1 語ずつ。検査の表からしか呼ばれない |
| 波形メモリのまとめ読み・まとめ書き | 0x8C2625D8（書き）・0x8C262644（読み、指令 0xD000）ほか。**スレーブ側（0xB8080000）のチップ**の同じレジスタを使い、番地と語数を受け取る。0x8C268954 が関数の番地を 0x8C3BEF40〜4C に並べる。鍵盤版のサンプル周りの名残らしい |
| 画面の文言 | `Receiving sample...` / `Transmitting sample...` が表に残っている（0x8C145CDC）。使われているかは未確認 |

まとめ読みのルーチンまで MIDI（SysEx）から届く道があるかは、**まだ追えていない**。
`F0 43` を見分けている場所が 40 か所以上あり、振り分けの表を読むのが次の仕事。

## サービスマニュアルとの突き合わせ（DM 基板）

| 位置 | 部品 | 役目 |
|---|---|---|
| IC25 | HD6417727F160 | CPU（SH7727、160MHz 品） |
| IC22, IC27 | T8F02TB-0102（X0060A00） | **SWP50**。音源チップ、マスターとスレーブ |
| IC36, 37, 38 | µPD23C128000（128Mbit のマスク ROM） | 波形 ROM の L1・L2・L3 |
| IC39, 40, 41 | 同上 | 波形 ROM の H1・H2・H3 |
| IC32, IC33 | フラッシュ ROM | **IC32 = データ、IC33 = プログラム**（RACK ES のサービスマニュアルの呼び方） |
| IC26, 29, 30, 31 | W986416DH（64Mbit の SDRAM） | CPU の RAM と、音源のエフェクト用。検査の「Main IC-29,30 / Efct IC-26,31」と合う |

* プログラムの検査画面に出る位置番号が、鍵盤版の部品表とそのまま合う。
  **RACK ES と鍵盤版は、CPU・音源・波形 ROM の周りが同じ設計**と見てよい
* 波形 ROM は L と H の 2 個で 32bit 幅、それが 3 組。検査の表の読み方（3 区画、偶数と奇数）と合う
* 検査の説明（T25）も「各 ROM の決まった番地群を読んで正規の値と比べる」で、コードの読みと同じ
* SWP50 のピン: レジスタ用のバス（CA・CD）、波形メモリのバス（HMA/HMD と LMA/LMD）、
  DIMM・SDRAM 用のバス、エフェクト用の DRAM のバス、チップ間の直列の音の線（MELI0-7 / MELO0-7）、
  マスター・スレーブの切り替え（SLAVE）。**SWP30 と同じ考え方の、ひと回り大きいチップ**に見える
* 鍵盤版にあって RACK に無いもの（DIMM のサンプリング RAM、mLAN、鍵盤）は当てにできない

## RACK ES のサービスマニュアルから（2026-10-12）

RACK ES そのもののサービスマニュアルが見つかった。`pdftotext -layout` で文字に起こせる
（日本語の部分は化けるが、英語の部分は読める）。エミュレーターに関わるところだけ拾った。

### フラッシュは 2 個、更新データも 2 種類

* IC33 が **プログラム**、IC32 が **データ**
* 更新の章（OS UPDATE）は「**PROGRAM ROM updater** と **DATA ROM updater** の両方を、サービス用のサイト
  （YSISS）から落とす」と書いている。一般に配られている `firm103.mid` は前者だけ。
  **データの側の更新ファイルも世の中には在った**ことになる（手元には無い）
* 更新を受ける状態にするには、[EXIT]・[PAGE>]・[MUTE/SEL/ENTER] を押したまま電源を入れる。
  起動すると今の版が出る。MIDI でも USB-MIDI でも受ける。送りは約 30 分、そのあと書き込みに約 3 分

### 電源を入れたあとの流れ（SYSTEM FLOW CHART）

1. CPU のリセット → **フラッシュのプログラムの区画を SDRAM へ写す** → CPU の初期化（ミュート）
2. SIO4 と E-Bus をリセット、液晶のコントラスト、`YAMAHA` を出す
3. **SWP50 の初期化**（ここから検査プログラムに入れる）
4. フラッシュのデータの区画を調べる。正しければ SDRAM へ写す。**壊れているか、控えてある版がプログラムの版と
   違えば、SDRAM を工場出荷の中身にして、データの区画へ書き戻す**
5. `Now Checking System Memory` → ミュート解除 → USB-MIDI → `Now Checking Plug-in Board`（約 6 秒）→ 初めの画面

フラッシュに残るものは User Voice・User Multi・User Performance・Utility・Plug-in Voice。
`Flash Data NG` や `Now Checking System Memory` の文言は Firm に無いので、4 までは Kernel の仕事と見ている。

### 検査プログラム

* 手で入る: [BANK>]・[VOICE]・[UTILITY] を押したまま電源を入れる。Firm・Kernel・Data の版が出る
* MIDI で入る: 起動して演奏できる状態になってから `F0 43 10 18 5A 00 F7`。以後は `A0 <検査の番号> 00` で 1 つずつ動かし、
  結果は `A0 <番号> 02`（OK）/ `03` 以降（NG）で返る
* T10 = フラッシュの ID の読みと、波形 ROM の決まった番地の照合。T11 = CPU の SDRAM とエフェクトの SDRAM の読み書き
* **T12（番号 0x0C）は Factory Set で、ユーザーのデータを全部消す。** T13 は終了（再起動）
* T06・T07 は 1kHz の正弦波を左・右に出す。光と同軸のデジタル出力も検査の対象

### デバッグ用の口（DM 基板の回路図、PDF の 104 ページ）

回路図のページは `inkscape --pages=104 --pdf-poppler --export-type=png --export-dpi=230` で絵にして読んだ
（文字は線になっていて `pdftotext` では拾えない。図は 90 度回っている）。

* **CN17「ROM-ICE & J-TAG」**（Molex 55091-0604、60 ピン）。回路図では **Not installed**（部品は付いていない。
  基板にランドが残っているかは実物を見ないと分からない）
* CN17 に来ている線: A[1]-A[23]（1-24 番）、/INH（26）、/PRGMCS（29）、/RD（31）、D[0]-D[15]（33-48）、
  J-TCK（51）、J-TDI（53）、J-TMS（55）、J-/TRST（57）、J-/ASE（59）、J-TDO（60）。50-58 の偶数は GND
* CPU の側は TCK・TDI・TMS・/TRST・/ASEBRKAK・TDO がこの束につながり、10k でプルアップ（RA62・R301・R312）。
  **/ASEMD0 は 22k でプルアップ、GND へ落とすスイッチ SW2 は Not installed**
* **基板の図（PDF の 21 ページ、部品面）にはランドが描かれている。** 場所は IC32（データのフラッシュ）のすぐ隣で、
  基板の縁（PLG のコネクター CN2-CN4 が並ぶ辺）に近い側。IC4 と C231 の間。1 番ピンの印（▼）は IC32 側の列の、IC4 寄りの端。
  SW1・SW2 のランドは CPU（IC25）と水晶 X6 のそば
* **ランドの番号の振り方（基板の図から決めた）**: IC32 側の列が奇数（▼ の端が 1 番、反対の端が 59 番）、
  基板の縁側の列が偶数（▼ の端が 2 番、反対の端が 60 番）。根拠は 2 つ。図の点の印が、奇数の列では 5・15・…・55 番、
  偶数の列では 10・20・…・60 番の位置に付いている。偶数の列のうち 28・30 番と 50-58 番のランドだけが、
  2 列の間の銅箔（GND）につながっていて、回路図の GND の番号とぴったり合う
* したがって JTAG の 6 本は **▼ と反対の端**に固まっている。IC32 側の列の端から 59（/ASE）・57（/TRST）・55（TMS）・
  53（TDI）・51（TCK）、縁側の列のいちばん端が 60（TDO）、その隣の 5 本（58-50）が GND
* 名前のとおり、プログラムのフラッシュの代わりに外の ROM エミュレーターをつなぐための口でもある
  （/INH で基板のフラッシュを黙らせる作り）。CPU のバスがそのまま出ている
* **波形 ROM はこのバスに居ない**（SWP50 の HMA/HMD・LMA/LMD の側）。この口から届くのは CPU のバスの上のもの
  （フラッシュ 2 個と SDRAM）まで
* SWP50 にも JTAG の端子があり、スレーブ（IC27）のものはテストランド TL6-TL10（TDI・TCK・TRST・TDO・TMS、
  10k でプルダウン）に出ている。マスターの側は未確認
* 回路図の隅に「IC32-33 FlashROM」の表（東芝 / 富士通、容量ごとの抵抗の付け方）と、
  「IC29・30 SDRAM」の表（64M / 128M / 256M）がある。フラッシュは AREA0（IC33）と AREA4（IC32）

### SH7727 の JTAG（H-UDI）でできること

ルネサスが公開している SH7727 のハードウェアマニュアル（REJ09B0254、31 章）から。

* H-UDI は JTAG（IEEE 1149.1）と互換の直列の口。**バウンダリスキャンに対応している**
* 命令レジスタ SDIR は 16bit で、上位 4bit が命令。載っている命令は EXTEST、SAMPLE/PRELOAD、バイパス、
  H-UDI リセット（かける / 解く）、H-UDI 割り込み、スリープからの復帰。**メモリを読む命令は載っていない**
* SDID（素性の番号）は H'0004200F。つないで最初に読めば、線が合っているかの確認になる
* バウンダリスキャンのレジスタ SDBSR は 392bit。表 31.3 に、D31-D0・A25-A0・/RD・/CS0 ほかの端子との対応が全部載っている
  （入力・出力・向きの制御の 3 種類のビット）
* **/ASEMD0 を L にして /RESETP をかけたとき（ASE モード）にだけ、バウンダリスキャンとエミュレーターの機能が使える。**
  H のまま（製品の状態）だと TCK・TMS・TDI・/TRST・TDO は入出力ポート（PTF4-7・PTE0）の側になる。
  RACK ES では /ASEMD0 は 22k で H に引かれていて、L に落とすのが取り付けられていない SW2。
  **CN17 に /ASEMD0 は出ていない**（59 番の J-/ASE は /ASEBRKAK）
* /ASEMD0 が L か開放のとき、/RESETP が効かなくなることがある、という注意書きがある
* 日立のエミュレーター（E10A）が使うデバッグの機能は「エミュレーターの説明書を見よ」とあるだけで、中身は載っていない
* 近い機種（SH7705）の技術情報に「バウンダリスキャンの間は CKIO のクロックを動かし続けること」とある。SH7727 でも同じかは未確認

### フラッシュ 2 個のつなぎ方（回路図から）

| | IC33（プログラム） | IC32（データ） |
|---|---|---|
| 回路図の見出し | AREA0（エリア 0） | エリア 4 |
| CPU から見た番地 | 0x00000000（P2 なら 0xA0000000） | 0x10000000（P2 なら 0xB0000000） |

* どちらも **48 ピンの TSOP、AMD 系と同じ並びの NOR フラッシュ**。/BYTE は 3.3V に固定で **16bit 幅**、/RESET も 3.3V に固定
* **フラッシュの A0 = CPU の A[1]**（A0-A18 = A[1]-A[19]）。DQ0-DQ15 = D[0]-D[15]。/OE = /RD。/WE は 11 番ピン
* CPU はビッグエンディアンなので、1 語の上位バイト（D15-D8）が若い番地のバイト
* ブロック図では IC32 に「**32Mb Data**」と書いてある（IC32 は 32Mbit）。IC33 の側は図が切れていて読めない
* 部品表の型番は `793V100 MAIN` / `793V100 SUB`（ヤマハの書き込み済み部品の名前）で、メーカーの型番は載っていない
* **容量とメーカーは基板の 0Ω の抵抗の付け方で決まる**（回路図の隅の表。左が IC32 用 / 右が IC33 用の番号）

| 抵抗（IC32 / IC33） | つなぐもの | 東芝 16 | 東芝 32 | 東芝 64 | 富士通 16 | 富士通 32 | 富士通 64 |
|---|---|---|---|---|---|---|---|
| R342 / R343 | A[22] → 13 番ピン | | | ○ | | | |
| R344 / R345 | A[22] → 9 番ピン | | | | | | ○ |
| R346 / R347 | A[20] → 15 番ピン | | | | | | ○ |
| R348 / R349 | A[20] → 9 番ピン | ○ | ○ | ○ | ○ | ○ | |
| R340 / R338 | 13 番ピン → RY/BY の線 | | | | | | ○ |
| R341 / R339 | 15 番ピン → RY/BY の線 | ○ | ○ | ○ | ○ | ○ | |
| R351 / R353 | A[21] → 10 番ピン | | ○ | ○ | | ○ | ○ |
| R352 / R354 | 書き込み保護の線 → 14 番ピン | | ○ | ○ | | ○ | ○ |

* Firm だけで 0x2C2800 バイト（2.76MB）あるので、**IC33 は 32Mbit（4MB）以上**のはず。IC32 の容量は実物の抵抗かチップの刻印を見て決める
* 富士通の 64Mbit だけピンの並びが違う（9・13・15 番）。読むときの番地の線の当て方が変わるので、先にどの組かを決めること
* バウンダリスキャンで読むなら: /WE を H のまま、番地を A[25:1] に出し、IC33 は /CS0、IC32 は /CS4 を L、/RD を L にして D[15:0] を読む
* **チップセレクトの線は回路図でたどって確かめた**（下の表）。IC33 の /CE は /CS0、IC32 の /CE は /CS4

| CPU の端子 | 直列の抵抗 | 線の名前 | 行き先 |
|---|---|---|---|
| 105 /CS0 | R232（47Ω） | /PRGMCS | CN17 の 29 番と、R356（0Ω）を通って **IC33 の /CE**（26 番ピン） |
| 106 /CS2 | R234（47Ω） | （名前なし） | 未追跡 |
| 107 /CS3 | R240（47Ω） | /SDRAMCS | SDRAM |
| 108 /CS4 | R241（47Ω） | /PRGSCS | **IC32 の /CE**（26 番ピン）へ直接 |
| 109 /CS5 | R244（47Ω） | /8-CS | 8bit 幅の周辺（0xB4000000 の側） |

## SWP50 のレジスタの使い方（2026-10-08、プログラムの静的な読みだけ）

コードから読めた事実、役目の名前は SWP30 からの類推で、後者には「らしい」を付けた。

道具は `tools/motif/` に置いた（`firm103.bin` のある場所で動かす）。

`src/motif/swp50test.cpp` が、ここに書いた手順どおりに返事をするかを確かめる（Makefile にはつないでいない。頭の注釈の 1 行で作る）。

### 番地の形

CPU から見た番地 = 土台（0xB8000000 / 0xB8080000）+ 語番地 × 2。語番地は 16bit で、

```
語番地 = a << 9 | r        a: 7bit（0-0x7F）  r: 9bit
```

* **r = 0x00-0x7D は「a 番のスロットのレジスタ」**。ボイスのドライバはスロットごとに
  0x400 バイトずつ進む（8C211EB0 の初期化は 0x40 回 × 2 スロット = **1 チップ 128 スロット**）
* **r = 0x7E・0x7F は制御レジスタ**で、a が番号になる。SWP30 の「0x0E・0x0F の列」と同じ考え方
* **r の bit 8（+0x100）は「溜めておく側」**。ここへ書いた値は、確定の合図を書くまで効かない（下）

これまでこのメモで「レジスタ << 8 | スロット」と書いていたのは、この形の読み違い
（0x207E は「a=0x10 の制御レジスタ 0x7E」）。語番地の値そのものは変わらない。

### 書き込みの口は 3 つある

| 口 | 場所 | 使い方 |
|---|---|---|
| ボイス側 | 8C211000-8C219FFF | オブジェクト（+0x0C に土台、+0x1E に先頭スロット）から番地を組んで**直接**書く |
| エフェクト側 | 8C21C7F0-8C21FC20 | 関数ポインタ経由。8C33D664 = 書き（既定 8C21CAD4）、8C33D668 = 読み（既定 8C21CAE6）。引数は R4 = チップ、R5 = 語番地、R6 = 値。土台の表は 8C10F53C |
| 検査・波形メモリ | 8C097000-8C09A8FF、8C261C00-8C262A20 | 番地をリテラルで持って直接 |

### まとめ書き（溜めて、合図で確定）

ボイス側（8C214336 で溜め、8C2143A0 で流す）とエフェクト側（8C21CAFC）が同じ仕組みを使う。

1. `r | 0x100` の番地へ、最大 8 個まで値を書く
2. 制御レジスタ **0x4A7E**（a=0x25）へ合図を書く。**ボイス側は 0x8000、エフェクト側は 0x4000**
3. 制御レジスタ **0x187E**（a=0x0C）の **bit 0 が 0 になるまで**読んで待つ（ボイス側は 0x4000 回で打ち切り）

エミュレーターでは「+0x100 の側に書かれた値を、合図で本体へ写す。0x187E の bit 0 は 0 を返す」で足りるはず。

ボイス側がこの口で書く r: 0x01・0x02・0x05・0x06・0x09・0x10・0x15、0x30-0x3E の偶数。

### スロットのレジスタ（ボイス）

8C211EB0（全スロットの初期化）が書く値。r は語の番号。

| r | 初期値 | |
|---|---|---|
| 0x00 | 0x0F00 | |
| 0x01 | 0x0080 | |
| 0x02 | 0x0000 | |
| 0x03 | 0x0020 | |
| 0x04 | 0x0030 | |
| 0x05-0x07 | 0 | |
| 0x08 | 0xAF00 | |
| 0x0B | 0 | |
| 0x10 | bit 12 と 13 を立て、bit 14 を落とす | 読んでから書き戻す。ビットごとの旗らしい |
| 0x14 | 0x7EFF | |

* ボイス側はほとんどが「読む → 一部のビットだけ替える → 書く」。替えるビットの切れ目は
  0xFF00 / 0x00FF / 0x7F00（0x80FF で消す）/ 0x8000 / 0xF000 / 0xFC00 が多い。
  **1 語に 8bit の値が 2 つ、または 7bit + 旗 1bit** という詰め方で、SWP30 の 16bit 丸ごとの値とは違う
* サンプルの出し入れ（8C261C78）は a = 0x7E・0x7F のスロットの r = 0x09・0x0A・0x10・0x19・0x1A・0x1B を使う

### ボイスの発音の流れ（2026-10-08 追記）

ボイス側のドライバはオブジェクトの形をしている。メソッド表は 8C0E03F8（124 本）で、
オブジェクトの +0x34 に入る。呼ぶ側は `[表 + 番号 × 4]` を引く。同じ形の表がもう 2 つある
（8C0E05E8、8C0E07D8。以下は 8C0E03F8 の話）。8C0E05E8 の側は、組を選ばずいつもスロット n へ書く版の関数
（8C213152 など）を指していて、**1 ボイス 1 スロットで鳴らす別の型**らしい。それ以上は読んでいない。

メソッドは 2 種類に分かれる。

* **0-62 番: 値をオブジェクトに控えるだけ**（単位の換算と頭打ちをして、+0x38 以降の欄へ置く）
* **63 番以降: 控えた値をレジスタへ詰めて書く**

**1 つのボイスはスロット n と n + 0x40 の 2 つを使う**（n = 0-63）。波形・音程・EG は n 側だけに書き、
LFO・フィルター・送りは両方に書く。つまり **1 チップ 64 声**。

下の表の「番」は呼ぶ側の番号（表の先頭から数えたもの）。レジスタは語の番号 r。

#### LFO とフィルター（スロット n + 0x40 と n の両方にある）

呼ぶ側の中間層（8C20CB14、8C20B26E-8C20B796、8C20D4DA）を読んで決めた。LFO もフィルターも
**1 ボイスに 2 組**あり、メソッドは組の番号を受け取る。LFO は組 0 がスロット n + 0x40、
組 1 がスロット n に書かれる（8C2130F4）。フィルターの側も同じ作りに見える（組の番号を受け取り、欄も 2 組ある）。
つまり **r = 0x00-0x08 の並びはどのスロットにもあり**、n + 0x40 は「2 つめの LFO・フィルター・送り」を
受け持つスロット、という読みになる。

  組の欄 +0 に入る。**どのレジスタへ書くかは追えていない**（発音開始の中だろう）
* 「幅の旗 1bit + 残り」で小さい値を細かく、大きい値を粗く持つ形が、カットオフ・深さに共通している
* カットオフは基準からのセントで、8bit に縮めて渡す。**滑らかに動かすのはチップの側**ということになる

#### スロット n の残り

| r | 中身 | 根拠 |
|---|---|---|
| 0x14 の下位 8bit | EG の最後の段が向かう高さ。0xFF を書いて待ち、読み戻した今の高さ（>> 6 で 8bit）が届いたら次へ進む、という使い方をしている | 8C20DE3A-8C20DF4A |
| 0x1C | 8bit × 2。既定はどちらも 0xFF で、条件によって片方を別の値にする | 8C20E0D2 |
| 0x20-0x27 | 4 組の「8bit の番号 + スロット番号」と「2bit + 8bit の量」。**ボイスの音を 4 か所へ送る口**（下の「送りの 4 本」）。前は「入力をどのスロットから取るか」と見立てていたが、量の出どころをたどって改めた | 量は 0 か 0xFF か値（8C215A90-） |

読み戻しの種類のうち、98 番（8C213F02）は EG の今の高さを返す（14bit、上位 8bit を使う）。

#### 発音開始（64 番、8C2123EC）

書く順番。値の細部は機械的な追跡なので、順番とレジスタだけを当てにすること。

1. r = 0x09、0x00、0x1C
2. r = 0x20-0x27（4 組）
3. **r = 0x90 に 0x8000 つきの値**を、スロット n と n + 0x40 の両方へ
4. r = 0x0A（音程）、0x11-0x13（EG）、0x15（形式）
5. r = 0x16-0x1B（波形の番地 3 つ）
6. 制御レジスタ 0x587E を読む
7. r = 0x10 に、3 と同じ値を 0x8000 なしで書く

r = 0x90 は r = 0x10 に 0x80 を足した番地で、ここだけに出てくる。**0x80 を足した側 + bit 15 が
発音の引き金**らしい（未確認）。

#### キーオフ（65 番、8C212EFE）

r = 0x12 と 0x13 の bit 15 を落とし、r = 0x14 を「0x8000 | 速さ << 8 | 今の下位 8bit」にする。
91 番は r = 0x14 に bit 15 を立てるだけ（控えてある速さで）。

#### 読み戻し（8C214154）

制御レジスタ 0x5C7E に「種類 | スロット番号」を書き、**bit 15 が立つまで** 0x5C7E を読んで待ち、
0x5C7F から値を読む。種類 0x0400 が今の音程（69・70 番）。ほかの種類は 76-78・92-94・98 番が使う（未読）。
エミュレーターは bit 15 をすぐ立てて、音程なら r = 0x0A の値を返せば先へ進むはず。

#### 時間待ち（121 番、8C214314）

制御レジスタ 0x1C7E を読んで返す。呼ぶ側（8C20FC56）は、この値が決まった数だけ進むまで回る。
**サンプルごとに進む数え**らしい。引数が 1 のときは 0x1A7F に 0x8010、続けて 0x10 を書く（数えの初期化らしい）。

#### 送りの 4 本（r = 0x20-0x27）と、量の目盛り（2026-10-12）

前の表で「そのスロットへの入力を、どのスロットから取るか」と見立てていた r = 0x20-0x27 は、**ボイスの音を 4 か所へ送る口**だった
（偶数の r が送り先の番号、奇数の r が種類 2bit と量 8bit）。音色のパラメーターを扱う層（8C1D9960 と 8C1D9A52）までさかのぼって決めた。

* 8C1D9960 が 6 本の量を計算して 8C2CEDF8 に置き、8C1D9A52 が中間層の 6 つの関数（8C20F55C-）へ渡す。
  中間層はそれを +0x250 からの欄に控え、発音のたびに 4 本の送りへ書く（8C20F5EA-）

| 番 | 計算（p = 音色の側の構造体、q = もう 1 つの構造体、off = +0xBC からの語） | 行き先 |
|---|---|---|
| 0 | `曲線[p[0x15]] + 8`（0-255 に頭打ち） | r = 0x21 |
| 1 | `曲線[(p[0x12] + off[1] を 0-127 に収めたもの) × 係数[q[0x11]] >> 7]` | r = 0x23 |
| 2 | `曲線[(p[0x13] + off[2] を 0-127 に収めたもの) × 係数[q[0x12]] >> 7]` | r = 0x25 |
| 3 | `曲線[p[0x14]]` | r = 0x27（型が 0 か 2 のとき） |
| 4 | 0 | r = 0x27（型が 0 か 3 のとき） |
| 5 | 8 | 未追跡 |

* **量の目盛りは「減らす量」で、0x10 が 6dB（1 目盛り 0.375dB）、0 = そのまま、0xFF = 切る。**
  曲線の表 8C0AACBE（128 バイト）が 0-127 の音量を直す: 127 → 0x00、64 → 0x10、32 → 0x20、16 → 0x30、8 → 0x40、4 → 0x50、2 → 0x60、1 → 0x70、0 → 0xFF。
  つまり `−16 × log2(音量 / 128)`。SWP30 の減衰の目盛り（4.4 の固定小数）と同じ考え方
* 係数の表 8C0AA83C は 0-126 がそのまま、127 だけ 0x80（127 を 1.0 倍にするための細工）
* 1 番と 2 番にだけ、コントローラーで動く上乗せ（off）がある。**リバーブとコーラスへの送り（CC91・CC93 で動く）**と見ている。
  0 番（+8 = 3dB 下げ）がそのままの音、3 番がもう 1 つの送り、という並びになる。**どれが何かはパラメーターの表（Data List）と突き合わせていない**
* 8C1D9960 と同じ形の関数が、p の読む場所を変えて並んでいる（0x12・0x13・0x14・0x15 から始まる版が見える）。音色の種類ごとの版だろう
* 送りの量（r = 0x30-0x3E の偶数、既定値 0x2000）とは別物。あちらが何の量かは、これで逆に分からなくなった（パンや出口ごとの量かもしれない）

#### EG の中間層と、速さの目盛り（2026-10-12）

EG の中間層（8C209688-8C209902）は、**変わった値だけをチップへ書く仕分け**だった。層のオブジェクトの +0x0C に「変わった」の旗が並び、
旗ごとに「控えるメソッド → 書くメソッド」を呼んで旗を落とす。値そのものは、もう 1 つ上の層（音色のパラメーター側、8C1CF300 付近）が計算して入れる。

| 欄 | 旗 | 入れる関数 | 控える / 書く | 中身 |
|---|---|---|---|---|
| +0x208（32bit） | 0x0001 | 8C2092A6 | 38 / 84 | 初めの高さ |
| +0x210 | 0x8000 | 8C2092B2 | 39 / 85 | **アタックの速さ** |
| +0x212 | 0x4000 | 8C2092C0 | 40 / 86 | ディケイ 1 の速さ |
| +0x214 | 0x2000 | 8C2092CE | 41 / 87 | ディケイ 2 の速さ |
| +0x216 | 0x1000 | 8C2092DC | 42 / 88 | リリースの速さ |
| +0x218 | 0x0800 | 8C2092EA | 43 / 88 | もう 1 つのリリースの速さ（段が 5 のときだけ書く） |
| +0x21E | 0x0400 | 8C209304 | 44 / 89 | 高さ（+0x214 の値と一緒に渡す） |
| +0x220 | 0x0200 | 8C209312 | 未読 | 高さ |

* **プログラムの側が「今どの段にいるか」を持っている**（+0x1C の数。0-5）。もう過ぎた段の値は書かずに旗だけ落とす。
  EG を進めるのはチップだが、段の切り替わりはプログラムが見張っている、という作りになる
* 控えるメソッド（38-43）は、渡された値をそのまま欄へ置くだけ。換算はしていない

**速さの目盛り**（8C1CFF64 と、チップ側のメソッド 106・107）:

```
t      = 表[0x7F − 時間のパラメーター]          表 = 8C0DDA08（32bit × 128）
x      = t × 255 ÷ |高さの差|
速さ   = 表の中で x に当たる番号を探したもの（8C2160CC）
```

* 表 8C0DDA08 は**速さの番号（7bit）→ かかる時間**。0 番が 0x000D539D（873,373）でいちばん長く、**8 番ごとに半分**になり（8 番 = 0x0006A8FA）、
  終わりのほうは 0x81 で頭打ち。「1 オクターブ = 8 目盛り」の対数の目盛り
* 時間の単位は読めていない。サンプル数だとすると 873,373 は約 19.8 秒（44.1kHz）で、音源の EG のいちばん遅い値としてもっともらしい（見立て）
* 式に 255 が掛かるので、**表の時間は「高さを 255 ぶん動かすのにかかる時間」**。パラメーターの時間が同じなら、
  高さの差が小さい段ほど遅い速さを選んで、かかる時間をそろえている
* 前に「未読」と書いた定数の表 8C0DDA08 がこれ。同じ並びの 8C0DDC08・8C0DDE08・8C0DE008・8C0DE208 は、メソッド 108-111 が引く別の種類の表（EG の種類ごとだろう）

**高さの目盛り**（8C1CF540 付近。高さを +0x21E へ入れる 8C209304 の呼ぶ側）:

* 高さのパラメーター（上乗せを足して 0-127 に収めたもの）を、**表 8C0AAD3E（128 バイト）で 8bit に直して**渡す
* 表の中身: 127 → 0x00、64 → 0x20、32 → 0x40、16 → 0x60、8 → 0x80、4 → 0xA0、2 → 0xC0、1 → 0xE0、0 → 0xFF。
  `−32 × log2(値 / 128)` と最大 1 の差で合う。**送りの表（8C0AACBE）のちょうど 2 倍**
* つまり EG の高さも**「減らす量」で、0 がいちばん大きく、0xFF が無音**。向きは送りの量と同じ。
  キーオフのあと「高さ 0xFF を書いて、今の高さが届くまで待つ」という使い方とも合う
* 2 倍になっているのは、パラメーターを 2 乗して効かせるため（音量のパラメーターが半分で 12dB 下がる、ヤマハでよくある決め方）と見ている。
  そう読むと、**チップの側の目盛りは送りと同じ「0x10 = 6dB」**で、表が違うだけ、ということになる。
  ただしこれは 2 つの表の形からの見立てで、チップが EG の 8bit をどう音量に直すかを直接読んだものではない
* 読み戻しの「今の高さ」は 14bit で、上位 8bit がこの目盛り、下位 6bit が端数（前に読んだ「>> 6 で 8bit」）

#### r = 0x30-0x3E の正体: 5 語ずつ 3 組の係数（2026-10-12）

「送りの量」と呼んでいた r = 0x30-0x3E は、送りではなく、**5 語ずつ 3 組の係数**だった（書くメソッド 95 番 = 8C213BEC、控える 48 番 = 8C215910）。

| 組 | 書く先（まとめ書き） |
|---|---|
| 0 | スロット n + 0x40 の r = 0x30・0x32・0x34・0x36・0x38 |
| 1 | スロット n の r = 0x30・0x32 と、スロット n + 0x40 の r = 0x3A・0x3C・0x3E |
| 2 | スロット n の r = 0x34 から先 |

* 3 組 × 5 語 = 15 語で、スロット n + 0x40 の 8 本とスロット n の 7 本にちょうど収まる（前の表の「8 本と 7 本」の理由）
* 組の数はチップのオブジェクトの +0x30 で、**64 声の型は 3、128 声の型は 2**（LFO とフィルターの組の数 +0x2E・+0x2F が 2・2 と 1・1 なのと同じ並び）
* 控える側は、組ごとに 3 語を受け取って 5 語のうちの 3 か所へ置き、残りを 0 にする。組 0 なら r = 0x34・0x30・0x36 の順
* 初期値は r = 0x34 と r = 0x3A だけ 0x2000、ほかは 0。**0x2000 を 1.0 とする係数（2.13 の固定小数）で、初期値は「素通し」**と読める
* 「5 語の係数が 3 組、素通しが初期値」という形から、**エレメントごとの EQ（2 次のフィルター 3 段）の係数**と見ている。
  MOTIF ES のエレメントには EQ（2 バンド・パラメトリック・ブースト）があり、3 語で足りる型と 5 語要る型がある、という辻つまになる。**見立て**
* 3 語を渡す側は、層のオブジェクトの +0x228 から 10 バイトずつ（8C20BAD0 が写す）。その値を計算している所へは、たどれていない
  （8C20BAD0 は層のオブジェクトの欄 +0x6C に入れられ、`[obj + 0xC8] + 0x6C` や `[obj + 0x10] + 0x6C` をたどって呼ばれる。
  `mr_slots.py slot 6c` で呼ぶ側の候補が 5 か所出るが、同じ番号の欄を持つ別のオブジェクトが混ざるので、どれが本物かはまだ決めていない）

#### 波形の情報がチップへ届くまで（2026-10-14、見出し探しの途中）

目的は、波形 ROM の「見出し」（鍵ごとのサンプルの割り当て、番地、ループ、元の音程）の形を知ること。**まだ見出しを読む場所には届いていない。** 途中で分かった所まで。

* **発音の直前に、層のオブジェクトの +0xDC からの 0x24 バイトを SWP50 へ渡す関数がある**（8C216808。8C20BF1C から呼ばれ、続けて発音開始の 64 番が呼ばれる）。
  中身と、渡す先のメソッド（表の先頭から 0-9 番）:

| 欄（+0xDC から） | 渡す先 | チップのオブジェクトでの扱い |
|---|---|---|
| +0x00（32bit） | 0 番 | 表 8C0D9490（`06 04 02 00 00 00`）を引いて +0x38 へ。**形式**（r = 0x15 と r = 0x09 の bit 14 へ行く値） |
| +0x04（バイト） | 1 番 | 8 倍して +0x39 へ |
| +0x08（32bit） | 2 番 | 表 8C0D9496（`00 80`）を引いて +0x3A へ。5・6 番にも渡り、2 つの番地のどちらを +0x40 / +0x44 に置くかを決める |
| +0x0C（32bit） | 3 番 | 表 8C0D9498（`00 40`）を引いて +0x3B へ |
| +0x10（32bit） | 4 番 | **始まりの番地**（+0x3C。r = 0x1A・0x1B へ） |
| +0x14・+0x18（32bit） | 5・6 番 | **あと 2 つの番地**（+0x40・+0x44。r = 0x16-0x19 へ。ループの始まりと終わりだろう） |
| +0x1C・+0x1D（バイト） | 7・8 番 | +0x48（半分にして 7bit）・+0x49 |
| +0x20（32bit） | 9 番 | 表 8C0D949A を引いて +0x4A へ |

* この 0x24 バイトを埋める関数が 1 つ見つかった（8C1D60F8）。**0x18 バイトの記録**から写す:
  記録の +0x00・+0x04・+0x08 = 番地 3 つ（32bit）、+0x0C = 16bit の値（層の +0x100 へ。音程の計算に使う欄なので、**元の音程**だろう）、
  +0x15・+0x16・+0x17 = 形式の 3 バイト。記録の残り（+0x0E-+0x14）は使っていない
* ただしこの関数を呼ぶのは 8C1D62E4 だけで、その呼ぶ側は 8C264A58・8C264D20・8C2663D0（**サンプルの出し入れの領域**）。
  記録は番地を引数でもらって、形式を決め打ち（3・0・1）で組み立てている。つまりこれは**録ったサンプルを試し聴きする道**で、プリセットの波形の道ではない
* **プリセットの波形で同じ 0x24 バイトを埋める場所は、まだ見つかっていない。** 層から層へ 0x24 バイトを丸ごと写す所（8C1D636C の中）はある
* **前の読みの訂正**: 「波形 ROM から 20 バイトの記録を番号で読む層」（8C268A20 ほか）は、土台の番地が 0x04000000（波形 ROM の範囲 0-0x02FFFFFF の外）で、
  読む関数と書く関数が対になっている。**サンプル用の RAM（DIMM）の中の台帳**で、ROM の見出しではない
* Firm の中に、波形 1,859 本ぶんの番地が並んだ表は無い（増えていく 32bit の値の長い並びを全部当たった）。→ 表はデータのフラッシュにあった（次の節）

#### 波形の見出しは、波形 ROM ではなくデータのフラッシュにある（2026-10-14）

波形番号から下へたどって見つけた。**鍵とベロシティからサンプルを選ぶ表は、IC32（データのフラッシュ）の中にある。**

8C1FA13A（引数: 書き出し先、波形番号、鍵、ベロシティ。返り値 = 見つかった数、最大 2）:

```
波形番号 >= 0x744 なら 0 を返す（波形は 1-1859）
番号  = 16bit の表[波形番号]                表は 0x901D9C44 から（波形番号 × 2）
記録  = 0x9017956C + 番号 × 0x1C           1 つ 0x1C（28）バイト
記録を順に見て、鍵とベロシティが範囲に入るものを書き出し先へ写す（+0x0C の 32bit だけ 2 倍にして写す）
記録の +0x13 の bit 7 が立っていたら、その波形の最後の記録
```

| 記録の中の位置 | 中身 |
|---|---|
| +0x00・+0x04・+0x08（32bit） | 未読（サンプルの番地の仲間だろう） |
| +0x0C（32bit） | 写すときに 2 倍にする値（語の数をバイトに直すなど、単位の換算だろう） |
| +0x12 | 鍵の範囲の下 |
| +0x13 | bit 0-6 = 鍵の範囲の上、**bit 7 = その波形の最後の記録** |
| +0x14・+0x15 | ベロシティの範囲の下・上 |
| +0x10-0x11、+0x16-0x1B | 未読 |

* **0x90000000 番台は、エリア 4（物理 0x10000000）= IC32 を P1 から見た番地。** つまり表は IC32 の先頭から 0x17956C（記録）と 0x1D9C44（波形番号 → 記録の番号）にある
* 2 つの表の間は 0x606D8 バイト = **記録 14,106 個ぶん**。番号の表は 1,860 × 2 = 3,720 バイトで、0x1DAACC まで
* 同じ波形・同じ鍵・同じベロシティで最大 2 つまで拾う（ステレオの左右だろう）
* 兄弟の関数が 2 つある: 8C1FA204 は RAM の表（8C2D5D2C から、1 つ 0x24 バイト。形は似ていて +0x12-0x15 が鍵とベロシティ）を、
  8C1FA354 はサンプル用の RAM の台帳を見る。どれを使うかは呼ぶ側（8C1FA0F0 付近）が決める
* **これで、鍵ごとのサンプルの割り当て・番地・ループの情報は、波形 ROM を外さなくても、フラッシュを読めば手に入る**ことになる
  （フラッシュは CN17 の JTAG から届く範囲）。波形 ROM に入っているのはサンプルの中身だけ、という読みになる
* 前に「番地と鍵の割り当ては ROM の側にある」と書いたのは誤り。Firm の中に表が無かったのは、データのフラッシュの側にあったから

### 別の形のオブジェクト

8C20FFF0 付近（表 8C0E02D4 の側）は、波形の番地を r = 0x12-0x17 に、ほかを r = 0x20-0x2A・0x32-0x37 に
書く。上の表と番地が合わないので、**別の種類のスロット**（サンプリングの録り・鳴らしらしい）を扱う別の
オブジェクトと見ている。読んでいない。

### a ごとのデータ（エフェクト側）

エフェクトのドライバが、a を変えながら決まった r へ書くもの。SWP30 の MEG の
「定数・オフセット・LFO」と同じ並べ方に見える。a と a + 1 を組で書くものが多い。

| r | 書く値（読めた範囲） |
|---|---|
| 0x1E・0x1F | 0x1F は 0 を書いてから値。0x1E は値だけ |
| 0x28 | 番号 + 0x80 / + 0x81 を OR した値 |
| 0x29・0x2B | 0x300 を OR した値、0x3FF、0x100、0x200 |
| 0x2A | 上位 8bit と下位 8bit に別々の番号（0xC0 + n、0xC1 + n） |
| 0x2C・0x2D | 6bit の値に旗 |
| 0x31、0x40・0x41、0x50、0x52-0x54、0x59 | 未読 |

### エフェクト側の作り（2026-10-12 追記）

エフェクトのドライバ（8C21C7F0-8C21FC20）を、外から呼ばれる入口ごとに読んだ。
エフェクト 1 個ぶんの「ブロック」がオブジェクトになっていて、型ごとのコード（8C216A00-8C219F00。
前に「ボイス側」と書いた範囲に混ざっている）が、下の入口を呼んで値を入れる。

**SWP30 の MEG と違い、プログラム（命令の列）を送る口は見つからなかった。** 送っているのは
係数・32bit の値・曲線の表・ユニットごとの設定だけ。命令の並びはチップの側で決まっていて、
ユニットの種類と係数で形を変える作りに見える（見立て）。

#### ブロックのオブジェクトの欄

| 欄 | 中身 |
|---|---|
| +0x00 | チップの番号（16bit） |
| +0x02 | bit 0 = 表のメモリの選択（下の「曲線の表」） |
| +0x06・+0x08 | 止める・動かすビットの先頭と本数（0x887E・0x887F の 32 本のうち） |
| +0x0C | 初期化で 0x807E に書く値 |
| +0x10 | 係数の番号の土台（ブロックごとにずらす） |
| +0x12・+0x26 | ユニットの先頭と個数（1 チップ 64 個のうち） |
| +0x20 | 曲線の表の置き場（32bit の番地） |
| +0x24 | 係数の個数 |
| +0xD0 | 0 でないあいだ、控えにだけ書いてチップへは書かない（まとめて入れ替える間の旗） |
| +0xD8・+0xDC・+0xE0・+0xF0 | 控えの表（16bit の係数 / 32bit の値 / ユニットの 2 語 / 止めるビット） |

#### 係数（16bit × 1024）

8C21DA7E（控えに書く）→ 8C21D02C（チップへ書く）。番号 i = 型の中の番号 + 土台。

```
i < 0x200:  a = i >> 2,            r = 0x31 + (i & 3) * 4     → r = 0x31・0x35・0x39・0x3D
i >= 0x200: a = (i - 0x200) >> 2,  r = 0x33 + (i & 3) * 4     → r = 0x33・0x37・0x3B・0x3F
```

ボイスの送り（r = 0x30-0x3E の偶数）のすき間の、奇数の r に入っている。8C21CF56 が
ブロックの係数を全部 0 にする（番号の表 8C0EA580 を使う）。

#### 32bit の値（340 個）

8C21DAEC（控え）→ 8C21D0C6（チップ）。番号は**係数の番号 ÷ 3**。上位 16bit を r に、下位を r + 1 に書く。

```
j = i / 3
j < 0xAA:  a = j >> 1,           r = 0x48 + (j & 1) * 4       → r = 0x48/49・0x4C/4D
j >= 0xAA: a = (j - 0xAA) >> 1,  r = 0x4A + (j & 1) * 4       → r = 0x4A/4B・0x4E/4F
```

**係数 3 個と 32bit の値 1 個でひと組**、それが 341 組、という数え方になっている
（0x200 ÷ 3 = 0xAA で、係数の前半・後半の切れ目と合う）。32bit の値はディレイの長さ（メモリの番地）らしい。

#### 番号つきの書き込み口（8C21DA40）

制御レジスタ 0x8E7E に `(係数の番号 << 3) | 3bit の値`、0x8E7F に 16bit の値。
係数を 1 個だけ、鳴らしながら動かすときの口らしい（3bit は動かし方の指定だろう）。

#### 曲線の表を流し込む口（8C21D254）

| 語番地 | |
|---|---|
| 0x847E | `選択 << 7 \| 番地の上位`（選択 = オブジェクト +0x02 の bit 0） |
| 0x847F | 番地の下位 16bit |
| 0x8A7E | 状態。**bit 8 が 0 になるまで**読んで待つ（1 語ごとに 3 回読む） |
| 0x867E | データ。1 語書くごとに番地が進む |

型のコードが流しているものは、命令ではなく**曲線の表**だった。たとえば 8C216D46 の型は、
0x81 語（8C0E141C。0x4000 から 0x7FFF まで、16 点ごとに 0x800 上がる指数の曲線）、
0x102 語（8C0E151E。32bit で 0x00800000、0x0085AAC3…と 1 点ごとに 2^(1/16) 倍）、
0x81 語（8C0E1722）、0x1001 語（8C0E1824）を続けて置く。歪みやアンプの型が引く表だろう。
8C21D55E は同じ中身を選択 0 と 1 の両方へ書く。エフェクト用の SDRAM（IC26・IC31）が行き先と見ている。

エミュレーターでは「0x8A7E の bit 8 は 0 を返す。0x867E へ書かれた語を、選ばれたメモリの番地へ順に置く」。

#### ユニット（1 チップ 64 個、a = ユニットの番号）

| r | 書く入口 | 中身 |
|---|---|---|
| 0x40・0x41 | 8C21D592 ほか | 8bit の値（初期化で a = 1-14 に、オブジェクト +0x11 以降の 1 バイトずつ） |
| 0x50 | 8C21D464 | 初期化で a = 0-10 と 0x10-0x1A に `番号 × 16`、a = 11 と 0x1B に 0xA9 |
| 0x52-0x54 | 8C21D66C | 未読 |
| 0x58 | 8C21DE78 | 控えの表（+0xE0）の 1 語め。**まとめ書き**（8 個ずつ） |
| 0x59 | 8C21DE78 | 同じ表の 2 語め。直接 |

| 語番地 | |
|---|---|
| 0xB07E・0xB07F・0xB27E・0xB27F | ユニット 64 個ぶんの旗（1 ユニット 1bit）。ブロックの持ち分のビットを立てて書く（8C21DF58）。**0xB27F = ユニット 0-15、0xB27E = 16-31、0xB07F = 32-47、0xB07E = 48-63** |
| 0xB87E | 上の 4 語を書いたあとに 2 を書く（確定の合図らしい） |

| 0x887E・0x887F | ブロックを止めるビット（32 本）。立てると止まり、落としたあとは**読み戻してそのビットが 0 になるまで**待つ（1 万回で打ち切り、8C21D89C） |

型のコードの手順は「+0xD0 を立てる → 止める（0x887E/F）→ 表を流す → 係数と 32bit の値を入れる → 動かす」。
エミュレーターでは、0x887E・0x887F は書かれた値をそのまま返せば先へ進む。

### 制御レジスタの読み足し（2026-10-12、A-Bus の設定を探した結果）

回路図で、2 個の SWP50 が A-Bus で結ばれていると分かった（[motif-rack-es-swp50-pins.md](motif-rack-es-swp50-pins.md)）。
その向きや中身を決める設定を Firm から探した。**A-Bus の設定そのものは見つけられなかった。** 候補を 3 つ読んだら、どれも別の役目だった。

| 語番地 | 分かった役目 | 根拠 |
|---|---|---|
| 0xE07E-0xE67F | **E-Bus（I2C 風の直列）の送受信**。0xE07F = データ、0xE27F = 指令と状態（0xF8 で送り始め。状態の bit 5・4・3・2 を見る）、0xE67E = 割り込みの旗（bit 0。0 を書いて消す）、0xE67F = 初期化（0x0A のあと 0x0B）、0xE07E・0xE27E = 初期化で 0x10 | 8C09BAEA（初期化）、8C09BEC8（送り始め。相手の番号の表から 1 バイト出す）、8C09BF1C（割り込みの中身）。マスターにしか使わない（土台は 0xB8000000 だけ）。回路図で E-Bus につながるのもマスターだけ |
| 0x407E-0x467F、0x487E | **まとめて発音させる口**らしい。メソッド表の 63 番が、10 バイトの包みから 0x467F・0x467E・0x447F・0x447E（1 つめの表。4 語 = 64bit）または 0x407E まで（2 つめの表。8 語 = 128bit）を書き、最後に 0x487E へ、オブジェクト +0x08 の型 0・1・2 に応じて 0x8000・0x9000・0x8800 を書く | 8C2122C6・8C21234C。呼ぶ側（8C20FB7E・8C20FC10）は 0x4A バイトの記録を順に送り、間で時間待ち（121 番）を挟む。64bit = 1 チップ 64 声と合う。型の 3 通りは、SWP50 の KONTRG の端子（マスターとスレーブで発音をそろえる線）の使い分けと見ている |
| 0x967E、0x987E・7F、0x9A7E・7F | **チップの中の値の読み戻し**。0x967E に `番号 & 0x1FF`（後半の組は `| 0x200`）を書き、0x987E・7F（前半）か 0x9A7E・7F（後半）から 32bit を読む。符号つき | 8C21E3E6。スレーブへ 0x1EC か 0x1F7 を書く 8C253840 も同じ口で、0x8A7E の bit 4 が落ちるのを待ってから読む。メーター（音量の読み）らしい |

* **発音のビットの並び**（8C20FA64 が包みへビットを立てる）: チップの中の番号 n = スロット番号 − オブジェクトの +0x1E、
  語は n >> 4、ビットは表 8C0D5B30 の n & 15 番（1 << k）。包みの語 0-3 が 0x467F・0x467E・0x447F・0x447E へ行くので、
  **0x467F = ボイス 0-15、0x467E = 16-31、0x447F = 32-47、0x447E = 48-63**。包みは 0x4A バイトの記録の中に、チップごとに 10 バイト
  （頭の 1 バイトが「使う」の印）。記録は 3 つまであり、8C20FACC が順に送って、間で時間待ちを挟む（発音を 3 回に分けてずらす仕組み）
* 前にこのメモで 0xE07E-0xE67F を「チップの中の直列の口らしい」、0x407E-0x467F を「初期化で 8 語まとめて書く」と書いていたのは、上のとおり
* SWP50 の番地をリテラルで直接持っている場所は、検査・波形メモリ・サンプルの出し入れ・上の E-Bus で全部だった。
  **A-Bus の設定があるとすれば、関数ポインタ越しに書くエフェクト側**（0x6A7E-0x7C7E、0x827E-0x8E7F、0xB07E-0xB87E のうち役目が決まっていないもの）か、
  **設定が要らない作り**（チップの SLAVE の端子で向きが決まる）のどちらか
  → 前者だった。下の「エフェクト側の残り」

### エフェクト側の残り: つなぎ替えの口と、チップをまたぐ接続（2026-10-12）

エフェクト側の制御レジスタのうち、役目が決まっていなかったものを読んだ。**6bit の番号（0-63）で「どの線をどこへ」を指す
つなぎ替えの仕組み**になっている。値の詰め方はコードから読めた事実、役目の名前は見立て。

| 語番地 | 書く関数 | 値の形 |
|---|---|---|
| 0x687F / 0x6A7E | 8C21D5E8（2 番めの引数が 1 / 2） | `旗 << 8 \| (4bit) << 4 \| (4bit)`。4bit の 2 つはブロックのオブジェクトの +0x1F・+0x20 に控える。初期化（8C21D464）が両方を書く |
| 0x7A7E | 8C21EB4E | 0 を書く（下の 0x7C7E の表を空にする、と見ている） |
| **0x7C7E** | 8C21EB6E | `0x8000 \| (1bit) << 14 \| (1bit) << 13 \| (2bit) << 10 \| 通し番号 << 6 \| (線の番号 & 0x3F)`。通し番号は 8C33D688 の数えを 1 ずつ進めて取る |
| a の r = 0x2C（a と a + 1） | 8C21EC14 | `(5bit) << 7 \| (1bit) << 6 \| (6bit)`。a + 1 の側は値も + 1（ステレオの組） |
| 0x6C7E | 8C21ECB2 | 控えの語にビットを足して書く（使っている組の旗の集まり） |
| 0x727F | 同上 | `(6bit) << 8 \| (1bit) << 14 \| (1bit) << 6 \| (6bit)` |
| a の r = 0x2D | 8C21F066 | `0x40 + (線の番号 & 0x3F)`。組の相手は線の番号 + 1 |
| a の r = 0x2A（a と a + 1） | 同上 | `(0x40 + 線の番号 / 2) << 8 \| (0xC0 + 相手の番号)`、a + 1 の側は 0xC1 + |
| a の r = 0x2B（a と a + 1） | 同上 | 0x100 と 0x200（左と右の印らしい） |
| a の r = 0x1F（a と a + 1） | 同上 | 0（つなぐ前に消す） |

**チップをまたぐ接続（A-Bus の設定と見ているもの）**: 8C21F066 は、つなぐ元と先の**チップの番号が違うときだけ**、
次の手順を踏む（同じチップなら飛ばす）。

1. 送る側のチップで 0x7C7E に 1 行足す（8C21EB6A。通し番号と線の番号を登録）
2. 受ける側のチップでユニットを 2 個取り（8C21EC14）、r = 0x2C に受け口の番号を書く
3. r = 0x1F を 0、r = 0x2A・0x2B に相手と左右を書く

線・ユニット・受け口は、チップごとの持ち数の表（8C33D68C・8C33D690・8C33D694 が指す）から 8C21FD8C・8C21FD68・8C21FD1E が割り当てる。

* 回路図で 2 個の SWP50 を結ぶ音の道は A-Bus しか無いので、**0x7C7E が「A-Bus へ載せる線の登録」、r = 0x2C が「A-Bus から受ける口」**という読みになる。
  どちらのチップも送る側になれる作り（向きは固定ではなく、接続ごとに決まる）
* **A-Bus は、通し番号で区切られた枠に、6bit で選んだ線を載せて運ぶ**形に見える。枠がいくつあるか、1 枠が何 bit かは読めていない
* 確かめる手: 8C21F066 を呼ぶ側（表 8C24B710-8C24B71C 経由）で、元と先のチップがどう決まるかを読む。
  エフェクトのブロックがどちらのチップに置かれるか（インサーションはスレーブ、リバーブとコーラスはマスター、など）が分かれば、A-Bus に何が流れるかが決まる

### 固定の接続の表と、A-Bus の向き（2026-10-12）

接続を作る関数（先頭は 8C21F04E）を呼ぶ側をたどった。8C21F40E が「0x1C バイトの記録の表」を回し、
エフェクト側の初期化（8C21F536 の後半、8C21F628-）が表を渡している。

| 表 | 記録の数 | 中身（16bit の語で。+0 = チップ、+4・+8 = ユニットの組） | 渡す先 |
|---|---|---|---|
| 8C10F668 | 1 | チップ 0、ユニット 0・1 | 8C21F40E（出口） |
| 8C269E94 | 2 | チップ 0、ユニット 2・3 / チップ 0、ユニット 4・5 | 8C21F40E（出口） |
| 8C10F630 | 2 | チップ 0、ユニット 0・1 / チップ 0、ユニット 2・3 | 8C21F3A4（入口の側。8C21EDB0 が処理） |
| 8C10F684 | ― | 8C21F478 へ渡す包み。0x767E に `0x4000 \| (2 & 3) << 12`、a = 0x12・0x13 の r = 0x2D、0x767F・0x787E（値 0x0504）・0x787F | デジタル出力の設定と見ている |

* **出口の記録は 3 つとも、チップ 0（マスター）のユニット 0・1、2・3、4・5**。ここへ r = 0x2D で線の番号を書く。
  回路図の「マスターの MELO0・1・2 が DAC 3 個へ」と数が合うので、**ユニット 0-5 の r = 0x2D が、MELO0-2 の左右へ出す線の指定**と見ている
* 8C21F04E は、記録 1 つごとに**チップの番号を 0 から順に回し、記録のチップと違う番号のとき**に「またぐ接続」を作る。
  そのとき 0x7C7E へ登録するのは**回している側（= 相手のチップ）**、r = 0x2C・0x1F・0x2A・0x2B を書くのは**記録のチップ**
* 記録のチップは全部マスターなので、**固定の接続では「スレーブが A-Bus へ載せ、マスターが受ける」**。
  3 つのステレオの出口（メインと個別出力 2 組）それぞれについて、スレーブの音がマスターへ運ばれ、マスターが自分の音と合わせて DAC へ出す、という形になる
* 逆向き（マスター → スレーブ）の固定の接続は表に無い。仕組みとしてはどちら向きも作れるが、使っているのは片道だけ、と見ている。
  エフェクトのブロックを動的につなぐ側（8C21F69C・8C21F8C0・8C21F7D0）が逆向きを作るかは未読
* チップの土台の表 8C10F53C は `B8000000・B8080000` の 2 個で、続く語が 1 と 6

### 入口の側と、つないだ線の音量（2026-10-12）

* **入口の記録（表 8C10F630、8C21EDB0 が処理）**: 記録の +4・+8 が外から入る線の番号（0x7F は「無し」）。番号ごとに受け口のユニットを 1 個取り、
  r = 0x2C に `0x0F80 | 番号` を書く。表の中身は番号 0・1 と 2・3 なので、**外からのステレオ 2 組**。RACK ES の PLG スロット 2 つ（マスターの MELI0・MELI1）と合う
* r = 0x2C の上位 5bit は「どこから受けるか」で、**0x1F（= 0x0F80）が外からの入力（MEL）**、チップをまたぐ接続のときは別の値（A-Bus の枠）という使い分けに見える
* 記録の +0x0C・+0x10・+0x14・+0x18 の小さな数（1・0・2・2 など）は、チップごとの控え（8C33D68C が指す、0x0E バイトずつ）の語へビットを足すのに使う。
  足すビットは表 8C0EB20C（線 2 本ごとに 0x0100・0x0200…0x8000）と 8C0EB28C（0-3 と、その 4 倍）から引く。
  控えの語は 0x6E7E（+4）・0x727E（+8）・0x747E（+0x0A）へ書かれる。**線ごとの形式（語の長さや詰め方）の設定**と見ている
* **r = 0x1F は、つないだ線の音量の組**（8C21F69C）。`左 << 8 | 右` の 8bit ずつで、受け口のユニット a と a + 1 に書く。
  上の層（8C24B656）は値に 0x20 を足して 0xFF で頭打ちにしてから渡す。接続を作るとき（8C21F04E）はまず 0 を書いておく
* 前の節で「動的につなぐ側」と呼んだ 8C21F69C は、接続を新しく作るのではなく、**できている接続の音量を変えるだけ**だった。
  したがって A-Bus は、読めた範囲では「スレーブ → マスター」の固定の 3 組だけ。8C21F8C0・8C21F7D0 は未読

### 検査プログラムが手で組む音の道（2026-10-12）

検査プログラム（8C097000-8C09A8FF）は、ドライバを通さずに SWP50 のレジスタを直接たたく。音出しの準備をする 8C099610 は、
**2 個のチップの役目の設定と、スレーブ → マスターの線を手で 1 本つなぐ**手順になっていて、ドライバの読みの答え合わせになる。

| スレーブ | 0x027E | 0x2080 | 同上。マスターと値が違うのはここだけ |
| マスター | a = 0 の r = 0x2C / a = 1 の r = 0x2C | 0 / 1 | 受け口 2 つ（左・右） |

| マスター | a = 0x7F の r = 0x2A / 0x2B | `0xC1 \| 表[n]` / 0x200 | 右の送り先 |
| スレーブ | 0x7A7E | 0 | 線の登録を空に |
| スレーブ | 0x7C7E / 0x7C7F | 0x8001 / 0 | **線 1 を A-Bus へ載せる** |
| （対象は引数） | a = 0 の r = 0x50・0x52・0x53 | 0 | |
| （対象は引数） | a = 1 の r = 0x50 / 0x52 / 0x53 | 0x0B / 0x0800 / 0x2000 | ユニット 1 の種類と量らしい |
| （対象は引数） | 0x887E | 下位 2bit を落とす（& 0xFFFC） | ブロック 0・1 を動かす |

* ドライバの読みと合う点: 0x7A7E で空にして 0x7C7E へ 0x8000 つきで登録する、載せるのはスレーブ、受け口は r = 0x2C、送り先は r = 0x2A・0x2B に 0x100・0x200 の印
* 新しく分かった点: **0x027E がマスター 0x1000・スレーブ 0x2080**。A-Bus や同期の向きを決める設定は、これまで見つからなかったが、ここだと見ている。
  0xC0 + n / 0x58 + n の「n」は 8 通り（表の 8 行）で、出口 8 本（MELO0-7）のどれへ出すかの番号に見える
* **検査の領域にある音出しの関数（先頭 8C0995F4）は、波形 ROM を使わない。** ユニットの r = 0x58 に引数の値（周波数らしい）、r = 0x59 に 0xC000 を書き、
  ユニットの旗（0xB27F ほか）を立てて 0xB87E に 2 を書く。**ユニットは自前の発振器を持っている**ことになる
  （前に読んだ「r = 0x58・0x59 は控えの表の 2 語」は、エフェクトの LFO の速さと形と見てよい）
* **ただし、この関数が T06・T07 の 1kHz そのものだとは確かめられていない。** 関数の番地を指すリテラルも、そこへ飛ぶ相対分岐も
  イメージの中に見つからない（使われていない名残の可能性がある）。r = 0x58 に入る値は引数の構造体の +2 の語を 0x3FF で切ったもので、
  呼ぶ側が見つからないので **1kHz に当たる値は分かっていない**。検査の項目の表は 8C269A62 から（14 バイトの行、名前 8 文字）、
  その後ろの 8C269B2C の 13 本は、中身が RTS だけの差し替え口（登録する関数は 8C09ADCC から）で、検査の処理そのものではなかった
* `mr_slots.py unref` でも、この関数（8C099610 の所）は「どこからも指されていない」に入る。イメージ全体では 19,696 個のうち 478 個がそうで、
  **使われていない名残**と見てよい。リテラル・相対分岐・PC 相対の番地作り（MOVA）・レジスタ相対の分岐（BSRF）を全部当たって、届くものが無かった
* 同じ関数がほかに書くもの: 0x687E・0x687F・0x6A7E に 0xFF、ユニットの r = 0x1E に `バイト << 8 | バイト`、r = 0x20 に `0x4080 | 番号`、
  r = 0x21 に `0x300 | 値`、0x907E（値は引数）・0x907F（0x6000）、0x927E・0x927F（`0x3020 | 番号`）、0x947E・0x947F（`番号 | 0x40`）。
  0x90-0x94 は 2 回ずつ書く。役目は未読
* **ボイスを力ずくで止める手順**（8C09A736）: スロット n の r = 0x14 の bit 15 を落とす → 番地に 0x80 を足した側（r = 0x90）へ、
  スロット n + 0x40 と n の順に 0x8000 を書く → **0x587E の bit 15 が立つまで待つ** → 同じ 2 か所へ 0 を書く。
  発音開始（64 番）で見た「r = 0x90 に 0x8000 つきで書いて 0x587E を読む」と同じ口で、**0x587E の bit 15 は「引き金を受け取った」の返事**

### SWP30 と比べて

* 番地の考え方（スロット × レジスタ、端の 2 列が制御）は同じ。スロットが 64 → 128、レジスタの列が 64 → 512 に増えた
* 「溜めて合図で確定」は SWP30 に無い。まとめて同じサンプルで効かせるための仕組みだろう
* 波形メモリを制御レジスタ越しに読む口は SWP30 の wave direct access とほぼ同じ
* ボイスのレジスタは詰め方が違うので、SWP30 の表をそのまま当てはめることはできない

### 次に読むところ

* ボイスの残り: LFO の波形の種類の行き先、r = 0x03、r = 0x02 の上位 6bit、r = 0x10 の上位の旗、r = 0x20-0x27 の入力の指定（8C20F5EA-8C20F9D0 を読めば決まる）、EG の中間層（8C209688-8C209902）
* メソッド表 8C0E05E8・8C0E07D8 の側（もう 1 つのチップ用か、別の機種用か）
* エフェクトの残り: ユニットの r = 0x52-0x54・0x58・0x59 と a ごとの r = 0x1E・0x1F・0x28-0x2D の意味、0x8E7E の 3bit、
  型ごとのコード（8C216A00-8C219F00）が係数の何番に何を入れるか。型を 1 つ（ディレイなど形の分かりやすいもの）選んで、
  係数 3 個 + 32bit の値 1 個の組がどう使われるかを当てるのが近道
* ボイスの入力の指定の中間層（8C20F5EA-）: 量は層のオブジェクトの +0x250 から 5 本（16bit）、+0x25C が 0-3 の型で、
  4 本めの入力は型によって +0x256 か +0x258 を使う、までは読めた。何の量かは未読
* 定数の表 8C0DDA08・8C0DDC08・8C0DDE08・8C0DE008・8C0DE208（32bit × 128 個ずつ。8C2141A4 以降が番号で引く）と 8C0D9450（16bit）

## エミュレーターを作るのに足りないもの

| | 状態 |
|---|---|
| 本体プログラム（Firm） | 更新データから取れる |
| Kernel（起動と OS） | **無い。** これが無いと Firm は走らない（OS の呼び出し先が無い）。ただし下の「Kernel との境目」 |
| Data（音色など） | 無い。プリセットの音色名は Firm の中に見つからない（波形の名前の表は Firm にある）ので、プリセットは Data の側 |
| 波形 ROM 96MB | 無い |
| SH7727 の CPU | MAME に SH-3 のコアはある。内蔵周辺（特に USB）は手薄 |
| SWP50 | **MAME にも実装が無い。** SWP30 を土台に、レジスタへの書き込みと実機の音から解くことになる。エフェクトは MEG と違ってプログラムを送らない作りなので、中の計算は音から当てるしかない |

### Kernel との境目（2026-10-12）

* Firm が Kernel を呼ぶ口は **`TRAPA #31` だけ**（357 か所）。R0 に機能コード、引数は R4 から
* 機能コードは **標準の µITRON 3.0 のもの**（約 40 種類）。多い順に `chg_pri`（−27）らしいもの 53、`dly_tsk`（−85）35、
  `set_flg`（−48）33、`wup_tsk`（−39）21、`sta_tsk`（−23）20、`cre_sem`（−49）18、`cre_tsk`（−17）14、`cre_flg`（−41）14、
  `def_int`（−65）11。−153・−157・−158（メッセージバッファの仲間）は名前を確かめていない
* Firm は **0x8C020000 より下を指すリテラルを 1 つも持たない**。Kernel を番地で直接呼ぶことはない
* RAM は P2 側の写し（0xAC3Bxxxx）からも使う（691 か所）

つまり Kernel の実物が無くても、µITRON の呼び出しを受ける代役があれば Firm は走らせられる見込みがある。
**その代役（試験台）は書いていない**（この作業場では書く途中で止められる）。

Kernel・Data・波形 ROM は実機の中にしか無い。実機から読む手段が決まるまで、
エミュレーターの側で確かめられるのは「プログラムの静的な読み」までになる。
